# 출시 전 부하 검증

출시 전에 아래 두 비기능 요구사항을 만족하는지 확인하는 데 쓰는 스크립트다. 운영 서버에서는 돌리지 않고, 운영과 분리된 임시 환경에서만 돌린 뒤 그 환경을 내린다. 자동 테스트(CI)에는 넣지 않는다.

| 요구사항 | 기준 |
|---|---|
| 지도 조회 성능 | 장소 100만 건, 동시 사용자 300명에서 지도 영역 조회 p95 200ms 이하, 오류율 1% 미만 |
| 행사 초과 신청 방지 | 정원 200석 행사에 오픈 직후 2,000건이 몰려도 성공은 정확히 200건 |

## 1. 검증용 데이터 생성 (`seed/`)

운영 데이터를 복사하지 않는다. 대신 `seed/seed.sh`가 아래 규칙으로 가짜 데이터를 만든다.

### 실행

스크립트는 두 단계로 넣는다.

| 단계 | 파일 | 넣는 것 | 전제 |
|---|---|---|---|
| `base` | `seed/seed.sql` | 장소, 공공·박지 상세, 관리자 1명, 신청 회원, 본인확인 | 앱을 한 번 띄워 Flyway가 스키마를 만든 **빈 DB**. `spot`이나 `member`에 행이 하나라도 있으면 멈춘다 |
| `extra` | `seed/seed-extra.sql` | 관리자 5명, 배경 회원, 베이스캠프·멤버·합류 신청, 동행 후기, 회원 신고·제재, 감사 로그, 로그인 기록, 행사 신청·결제, 커뮤니티 글·댓글·좋아요·이미지, 추억 기록·사진·좋아요 | `base`를 마친 DB. `basecamp`, `member_report`, `sanction`, `community_post`, `memory` 중 하나라도 행이 있으면 멈춘다 |

두 단계 모두 조건이 맞지 않으면 아무것도 넣지 않고 오류로 멈춘다. 그래서 개발용 DB나 운영 DB에 잘못 돌려도 데이터가 섞이지 않는다. 로그인 기록, 행사, 감사 로그는 k6 스크립트도 남기므로 `extra`는 이 세 테이블이 비어 있는지 보지 않는다. 그래서 `base`만 넣고 k6를 돌린 볼륨에도 `SEED_STAGES=extra`로 두 번째 단계만 더할 수 있다.

```bash
# 로컬: 개발용 DB와 섞이지 않게 빈 데이터베이스를 따로 만든다
docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot -e \
  "CREATE DATABASE moewadeul_loadtest; GRANT ALL ON moewadeul_loadtest.* TO \"$MYSQL_USER\"@\"%\";"'
DB_NAME=moewadeul_loadtest ./gradlew bootRun          # 마이그레이션이 끝나면 그대로 둬도 되고 꺼도 된다
SPOT_COUNT=20000 MEMBER_COUNT=200 SEED_DB=moewadeul_loadtest load-test/seed/seed.sh

# 검증 서버: 운영 compose 파일로 띄운 MySQL에 기본값(장소 100만, 신청 회원 2,000)으로 넣는다
COMPOSE_FILE=/opt/moewadeul/docker-compose.prod.yml ENV_FILE=/opt/moewadeul/.env load-test/seed/seed.sh

# 첫 단계를 이미 넣은 DB에 두 번째 단계만 더한다
SEED_STAGES=extra SEED_DB=moewadeul_loadtest load-test/seed/seed.sh

# 로컬에서 두 단계를 작은 규모로 확인한다(약 15초)
SPOT_COUNT=20000 MEMBER_COUNT=200 EXTRA_MEMBER_COUNT=10000 BASECAMP_COUNT=5000 AUDIT_LOG_COUNT=2000 \
  LOGIN_HISTORY_COUNT=20000 PROGRAM_COUNT=10 POST_COUNT=3000 MEMORY_COUNT=2000 SEED_DB=moewadeul_loadtest load-test/seed/seed.sh
```

| 환경 변수 | 기본값 | 뜻 |
|---|---|---|
| `SPOT_COUNT` | 1000000 | 장소 수 |
| `MEMBER_COUNT` | 2000 | 신청 회원 수(관리자 1명은 따로). 최대 100,000 |
| `SEED_DB` | 컨테이너의 `MYSQL_DATABASE` | 데이터를 넣을 데이터베이스 |
| `ENV_FILE` | compose 기본값 | `docker compose --env-file`에 넘길 파일 |
| `COMPOSE_FILE` | 현재 폴더의 compose 파일 | docker compose가 직접 읽는 표준 변수 |
| `SEED_STAGES` | `base,extra` | 돌릴 단계. `base`, `extra`, `base,extra` 중 하나 |
| `EXTRA_MEMBER_COUNT` | 200000 | 배경 회원 수. 10,000~1,000,000 |
| `BASECAMP_COUNT` | 300000 | 베이스캠프 수. 1,000 이상 |
| `AUDIT_LOG_COUNT` | 100000 | 관리자 감사 로그 수 |
| `LOGIN_HISTORY_COUNT` | 3000000 | 로그인 기록 수 |
| `PROGRAM_COUNT` | 2000 | 지난 행사 수(행사마다 신청 50~299건). 다가오는 행사 1개는 따로 |
| `POST_COUNT` | 200000 | 커뮤니티 글 수. 1,000 이상 |
| `MEMORY_COUNT` | 100000 | 배경 회원의 추억 기록 수. 1,000 이상. 첫 신청 회원의 기록 1,000개는 따로 |

스크립트는 DB 비밀번호를 받지 않는다. MySQL 컨테이너 안의 `MYSQL_ROOT_PASSWORD`로 접속하므로 비밀번호가 인자나 셸 기록에 남지 않는다.

소요 시간: 로컬(Apple Silicon 맥, Docker의 MySQL 8.4)에서 장소 100만 건과 신청 회원 2,000명을 넣는 데 1,291초(약 21분) 걸렸다. 장소를 넣을 때마다 MySQL 트리거가 지도 묶음 집계 표 두 개를 8단계씩 고치기 때문이다. 트리거가 생기기 전에는 123초였다.

두 번째 단계(기본 규모)는 같은 로컬 환경에서 183초 걸렸다(2026-10-17, MySQL을 CPU 2개·메모리 640MB로 묶은 운영 compose). 넣은 행은 이렇다.
- 배경 회원 200,000명, 베이스캠프 300,000개, 베이스캠프 멤버 863,071행, 동행 후기 939,296건
- 회원 신고 51,057건, 제재 24,485건
- 행사 신청 350,096건, 커뮤니티 글 200,000개, 댓글 548,915건, 글 좋아요 1,207,288개
- 추억 기록 101,000개, 기록 좋아요 846,112개
- 로그인 기록은 이 단계에서 3,000,000건을 넣었다(그 볼륨에는 k6가 남긴 기록이 이미 있었다)

### 생성 규칙

**회원**
- 관리자 1명: `admin@loadtest.invalid`. k6 스크립트가 행사를 만들 때 쓴다.
- 신청 회원 `MEMBER_COUNT`명: `user000001@loadtest.invalid`부터 차례로. 이메일 인증을 마친 활성 회원이다.
- 비밀번호는 모두 검증용 가짜 값 `LoadTest#2026`이고, DB에는 그 BCrypt 해시만 들어간다. 이 회원들은 검증 환경에만 있고 운영에는 없다.
- 신청 회원은 모두 가짜 제공자로 본인확인을 마친 성인(출생연도 1970~2000년)이다. 그래서 숙박 행사에 신청할 수 있는 신뢰 단계 1이 된다.

**장소 `SPOT_COUNT`건**

| 항목 | 규칙 |
|---|---|
| 유형 | 박지 90%, 야영장 8%, 휴양림 2% |
| 상태 | 활성 97%, 검토 대기 1%, 숨김 2%. 검토 대기와 숨김은 박지에만 둔다 |
| 공원 경계 경고 | 박지의 10%. 경고 플래그만 켜고 공원 경계 데이터는 연결하지 않는다(지도 조회는 플래그만 읽는다) |
| 휴장 | 야영장·휴양림의 5%를 기간 없는 임시 휴장으로 둔다. 기간이 없으면 날짜와 상관없이 휴장이라서, 측정하는 날에 따라 비율이 바뀌지 않는다 |
| 상세 행 | 야영장·휴양림은 공공 장소 상세(외부 ID `LT-장소ID`), 박지는 박지 상세(제보자는 첫 신청 회원, 물·화장실 각 50%) |

실제 공공데이터는 야영장 약 4천 곳, 휴양림 약 200곳이다. 그래서 서비스가 커진다고 가정한 100만 건은 대부분 사용자가 제보한 박지로 채웠다.

**지역 분포**

스크립트는 장소마다 아래 시·도 중 하나를 가중치에 따라 고르고, 그 중심 좌표에서 정규분포(박스-뮬러 변환)로 흩뿌린다. 가중치는 공공 야영장의 시·도별 분포를 닮게 잡은 근사값이다. 결과 좌표는 위도 33.0~38.6, 경도 124.6~131.9 안으로 자르므로 일부 점은 바다나 북한 지역에 떨어질 수 있다.

| 강원 | 37.75, 128.30 | 17 | 0.35 |
| 경북 | 36.35, 128.75 | 9 | 0.35 |
| 경남 | 35.35, 128.25 | 8 | 0.35 |
| 충남 | 36.55, 126.85 | 7 | 0.35 |
| 충북 | 36.75, 127.75 | 6 | 0.35 |
| 전남 | 34.85, 126.95 | 6 | 0.35 |

| 인천 | 37.46, 126.44 | 4 | 0.08 |

| 서울·부산·대구·대전·광주·울산 | 각 시청 부근 | 각 2 | 0.08 |

기상청 격자 번호는 위경도를 선형 근사한 값이다. 검증 중에는 날씨 API를 부르지 않아서 정확한 격자가 필요 없다.

### 두 번째 단계 생성 규칙

규칙의 목표는 개선 후보 측정(#459·#460·#462)에 필요한 모양을 만드는 것이다. 예를 들어 "글 하나에 댓글 수천 건", "대상이 거의 없는 자동 처리 조회" 같은 모양이다. 그래서 실제 서비스의 분포를 흉내 내기보다, 재려는 경우가 확실히 들어가게 잡았다. 행마다 같은 값을 여러 번 써야 하는 난수는 `RAND()` 대신 `CRC32(소금 + 순번)`으로 만든다. 그래서 같은 규모로 다시 돌리면 같은 모양이 나온다.

**회원**
- 관리자 5명(`admin2`~`admin6@loadtest.invalid`)을 더해, 관리자 6명이 신고 처리와 감사 로그를 나눠 맡는다.
- 배경 회원 `EXTRA_MEMBER_COUNT`명: `bg0000001@loadtest.invalid`부터. 비밀번호는 신청 회원과 같고, 모두 본인확인을 마친 성인이다. 동행, 신고, 글, 좋아요는 모두 배경 회원이 맡는다. 그래서 k6가 로그인하는 신청 회원(`user*`)은 제재, 로그인 잠금, 베이스캠프 제한에 걸리지 않는다.
- 배경 회원 앞의 100명은 "많이 다닌 회원"이다. 완료 베이스캠프 50개에 하나꼴로 자리 하나를 이 100명에게 준다. 그래서 기본 규모에서 한 명당 완료 동행이 50번쯤 쌓인다(신뢰 단계 집계 측정용).

**베이스캠프 `BASECAMP_COUNT`개**

| 항목 | 규칙 |
|---|---|
| 상태 | 완료 85%, 취소 8%, 모집 중 5%, 마감(자동, 정원 참) 1%, 확정 1% |
| 날짜 | 완료·취소는 출발 5~724일 전, 모집 중·마감은 2~60일 뒤, 확정은 오늘 출발. 1~3박. 그래서 0시 자동 처리가 고를 행은 없다 |
| 정원·인원 | 정원 2~6. 완료·확정은 2명~정원, 모집 중은 1명~정원-1, 마감은 정원, 취소는 대부분 캠프 리더 혼자 |
| 합류 조건 | 60%는 조건 없음, 30%는 신뢰 단계 1, 10%는 2. 10개에 하나는 20~40대, 20개에 하나는 같은 성별만 |
| 캠프 리더 | 회원마다 캠프를 많아야 두세 개 연다. 그래서 모집 중·마감 3개 제한을 넘지 않는다 |
| 합류 신청 | 멤버마다 승인된 신청이 있다. 모집 중에는 대기 0~3건, 모든 캠프에 거절 0~2건·본인 취소 0~1건, 확정·완료·취소에는 만료 0~1건 |
| 먼저 떠난 멤버 | 완료 20개에 하나는 출발 전날 떠난 멤버(임박 탈퇴) 한 명 |
| 붐비는 베이스캠프 | 1,000개에 하나. 모집 중, 정원 6, 캠프 리더 혼자, 대기 20건(상한), 거절 60건, 취소 10건. 합류 신청 잠금과 신청 목록 측정용이다 |

**동행 후기·신고·제재**
- 완료 베이스캠프의 멤버 쌍마다 절반 꼴로 동행 후기를 쓴다. 완료 뒤 14일 안에 쓰고, "다시 동행" 90%, 태그는 1~2개다.
- 완료 베이스캠프 다섯에 하나꼴로 멤버 한 명이 캠프 리더를 신고한다. 유형은 성희롱·위협 3%(급함), 금전 요구 10%, 나머지 네 유형을 고르게 둔다. 처리 상태는 조치 45%, 기각 40%, 접수 10%, 검토 중 5%다.
- 조치한 신고마다 제재 하나를 둔다(경고 50%, 정지 7일 30%, 30일 15%, 영구 5%, 그중 5%는 해제). 성희롱·위협 신고에는 72시간 임시 정지가 먼저 붙는다. 끝난 정지는 만료 상태이고, 활성 정지가 남은 회원은 이용 정지 상태다.

**감사 로그·로그인 기록·행사**
- 감사 로그 `AUDIT_LOG_COUNT`건: 관리자 6명이 지난 1년 동안 남긴 조치 14종을 고르게 흩뿌린다.
- 로그인 기록 `LOGIN_HISTORY_COUNT`건: 배경 회원 이메일로만 남긴다. 98%는 최근 3개월 안(1시간 전보다 이전), 2%는 3~6개월 전이고, 성공 90%다.
  - 로그인할 때 서버는 입력한 이메일의 최근 실패를 센다. 그런데 `attempted_email`에 인덱스가 없어서, 이 표가 클수록 모든 로그인이 느려진다. 그래서 k6의 행사 오픈 스크립트처럼 로그인이 많은 측정은 이 점을 조건에 적는다.
- 지난 행사 `PROGRAM_COUNT`개(정원 300, 참가비 3만 원)에 신청을 50~299건씩 둔다(확정 80%와 결제 완료, 본인 취소 10%, 결제 만료 10%). 다가오는 행사 하나에는 결제 대기 20건이 있다. 기한이 24시간 뒤라서, 1분마다 도는 결제 만료 작업이 그동안 고를 행은 없다.

**커뮤니티**
- 글 `POST_COUNT`개: 2년 동안 고르게 흩뿌리고, 5%는 장소에 연결한다. 활성 90%, 삭제 4%, 숨김 3%, 검토 대기 3%다. 다만 순번 30~35% 구간은 95%가 활성이 아니다(최신순 목록이 오래 훑는 구간).
- 본문은 80%가 짧고(약 130~540자), 20%가 길다(약 1,900~5,400자). 모든 글에 "백패킹"이 들어가고, 1만 개에 두 개꼴로 희귀 낱말 "lt희귀토큰"이 맨 앞에 들어간다.
- 가장 최근 활성 글 다섯 개는 "붐비는 글"이다. 최상위 댓글 3,500건, 답글 1,500건, 좋아요 3,000개다. 다른 글은 최상위 댓글 0~11건(대부분 0~2건)이다.
- 댓글은 활성 92%, 삭제 5%(내용 없음), 숨김 2%, 검토 대기 1%다. 답글은 같은 글의 최상위 댓글에만 단다.
- 좋아요: 60%는 0개, 25%는 1~2개, 10%는 3~5개, 5%는 5~304개다. 서버가 저장하는 글의 좋아요 수(`like_count`)도 좋아요 행 수로 채운다. 이미지는 열 개에 하나꼴로 1~5장이다.

**추억 기록**
- 첫 신청 회원(`user000001`)에게 기록 1,000개와 사진 3,000장을 몰아준다(공개 40%). 내 기록 목록 측정용이다.
- 배경 회원의 기록 `MEMORY_COUNT`개: 공개 75%, 활성 95%·숨김 3%·검토 대기 2%, 사진 0~5장. 좌표는 무작위 활성 장소의 좌표이고 절반은 그 장소에 연결한다.
- 공개 기록의 좋아요: 50%는 0개, 30%는 1~3개, 15%는 4~15개, 5%는 16~515개다.

**넣지 않는 것**: 탈퇴 회원과 CI 보관 기한, 혼자 가는 일정, 장소 후기, 알림, 커뮤니티·기록 신고, 동행 후기 신고(`INAPPROPRIATE_REVIEW`). 제재받은 캠프 리더의 모집 중 베이스캠프도 정리하지 않는다(실제로는 제재 확정 때 서버가 취소한다).

## 2. k6 스크립트

k6는 앱과 다른 머신에서 돌린다. 같은 머신에서 돌리면 k6가 CPU를 나눠 써서 앱의 응답 시간이 실제보다 나쁘게 나오기 때문이다. 로컬에서 작은 규모로 돌리는 것은 스크립트가 도는지 확인하는 용도이고, 그 수치로 기준을 판정하지 않는다.

| 파일 | 하는 일 |
|---|---|
| `map-area.js` | 지도 영역 조회. 가상 사용자(VU) 300명이 각자 화면 영역을 하나 골라 조회하고 1~3초 쉬기를 반복한다 |
| `program-open.js` | 행사 오픈 순간 신청. 준비 단계에서 회원을 모두 로그인시키고 행사를 만든 뒤, 신청이 열리는 순간 모든 회원이 한 번씩 신청한다 |
| `spot-nearby.js` | 반경 검색. VU마다 시·도 가중치로 중심을 고르고, 반경·조건·페이지를 섞어 검색한 뒤 1~3초 쉬기를 반복한다(#457) |
| `spot-detail.js` | 장소 상세. VU마다 장소 ID를 무작위로 골라 상세를 조회하고 1~3초 쉬기를 반복한다(#457) |
| `lib/auth.js` | CSRF 토큰 받기, 로그인, 인증 헤더 만들기 |
| `lib/regions.js` | 시·도 중심 좌표와 가중치. `seed/seed.sql`과 같은 값이다 |

### 실행

```bash
# 로컬, 작은 규모 (1절의 로컬 예시로 장소 2만 건과 신청 회원 200명을 넣은 상태)
k6 run -e VUS=10 -e DURATION=30s load-test/map-area.js
k6 run -e APPLICANTS=200 -e CAPACITY=20 -e OPEN_DELAY=5 load-test/program-open.js
k6 run -e APPLICANTS=200 -e CAPACITY=20 -e OPEN_DELAY=5 -e OVERNIGHT=false load-test/program-open.js
k6 run -e VUS=10 -e DURATION=30s -e HIDE_CLOSED_RATIO=0.3 load-test/map-area.js
k6 run -e VUS=2 -e DURATION=30s -e RADII=1,5 load-test/spot-nearby.js
k6 run -e VUS=10 -e DURATION=30s -e SPOT_MAX_ID=20000 load-test/spot-detail.js

# 검증 환경, 기준 조건 (결과는 gitignore된 load-test/results/에 남긴다)
k6 run -e BASE_URL=http://앱-서버-사설-IP --summary-trend-stats "avg,med,p(95),p(99),max" \
  --summary-export=load-test/results/map-area-1.json load-test/map-area.js
k6 run -e BASE_URL=http://앱-서버-사설-IP --summary-trend-stats "avg,med,p(95),p(99),max" \
  --summary-export=load-test/results/program-open-1.json load-test/program-open.js
```

| 환경 변수 | 기본값 | 스크립트 | 뜻 |
|---|---|---|---|
| `BASE_URL` | `http://localhost:8080` | 둘 다 | 앱 주소 |
| `LOADTEST_PASSWORD` | 검증용 가짜 비밀번호 | 둘 다 | 검증 회원 비밀번호. 1절 데이터를 썼다면 바꾸지 않는다 |
| `VUS` | 300 | `map-area.js` | 동시 사용자 수 |
| `DURATION` | `10m` | `map-area.js` | 측정 시간 |
| `HIDE_CLOSED_RATIO` | 0 | `map-area.js` | 휴장 제외를 켠 요청의 비율(0~1). 화면 기본값은 꺼져 있어서 0이면 예전 측정과 같은 요청만 보낸다 |
| `VUS` | 10 / 300 | `spot-nearby.js` / `spot-detail.js` | 동시 사용자 수 |
| `DURATION` | `2m` | `spot-nearby.js`, `spot-detail.js` | 측정 시간 |
| `RADII` | `5,10,20,50` | `spot-nearby.js` | 고를 반경(km) 목록. 같은 비율로 고른다 |
| `SPOT_MAX_ID` | 1000000 | `spot-detail.js` | 고를 장소 ID의 최댓값. 검증 DB의 `SELECT MAX(id) FROM spot` 값을 넣는다 |
| `APPLICANTS` | 2000 | `program-open.js` | 신청 회원 수. 1절의 `MEMBER_COUNT`보다 많으면 로그인에 실패한다 |
| `CAPACITY` | 200 | `program-open.js` | 행사 정원 |
| `OVERNIGHT` | `true` | `program-open.js` | 숙박 행사 여부. 숙박 행사는 서버가 신청마다 신뢰 단계를 계산한다 |
| `OPEN_DELAY` | 20 | `program-open.js` | 준비가 끝난 뒤 신청이 열리기까지 기다릴 초 |

### 지도 영역 조회 (`map-area.js`)

- 판정: `spots-area` 요청의 p95가 200ms 미만이고 실패율이 1% 미만이면 통과다. 스크립트는 응답마다 200인지, 마커와 묶음이 합쳐 500개 이하인지도 확인한다.
- 화면 영역: 카카오맵 확대 수준을 아래 비율로 섞는다. 사람이 전국 지도는 잠깐 보고 시·군이나 동네 단위로 들어가서 오래 본다고 가정했다. 13레벨이 아니면 화면 중심을 1절의 시·도 가중치와 정규분포로 고른다.

| 확대 수준 | 비율 | 화면 크기(경도 × 위도) | 뜻 |
|---|---|---|---|
| 13 | 10% | 7° × 5.6° (중심 고정: 36.3, 127.8) | 전국 |
| 10 | 30% | 0.875° × 0.7° | 시·도 |
| 8 | 40% | 0.22° × 0.175° | 시·군 |
| 5 | 20% | 0.027° × 0.022° | 동네 |

- 요약에는 확대 수준별 응답 시간(`level:13` 등)이 따로 나온다. 이 줄의 조건(`max>=0`)은 요약에 보이게 하려는 것이라 늘 통과한다.

- 휴장 제외 비율을 0보다 크게 주면, 요약에 휴장 제외 여부별 응답 시간(`hideClosed:true`, `hideClosed:false`)이 따로 나온다.

### 반경 검색 (`spot-nearby.js`)

- 반경 검색에는 수치 기준이 없어서 판정 조건을 두지 않는다. 요약에 반경별 응답 시간(`radius:20` 등)이 따로 나온다.
- 조건은 없음 60%, 물 있는 박지 20%, 휴장 제외 20%로 섞는다. 열 번에 한 번은 2~5쪽을 읽는다.
- 화면에서 반경 검색은 AI 검색이 문장의 거리를 읽었을 때 열린다. 그래서 지도 조회보다 요청이 훨씬 적다고 보고, 기본 VU를 10으로 잡았다.
- 검증용 데이터에서 반경 안 장소 수는 중심과 반경에 따라 크게 다르다. 예를 들어 경기 중심은 반경 5km에 약 2천 곳, 50km에 약 17만 곳이다.

### 장소 상세 (`spot-detail.js`)

- 장소 상세에는 수치 기준이 없어서 판정 조건을 두지 않는다.
- 검증용 데이터는 장소 ID 사이에 빈 번호가 있다. 빈 번호나 숨김·검토 대기 장소를 고르면 404가 나오고, 404는 장소를 읽지 않아 200보다 빠르다. 그래서 200 응답의 시간만 `spot_detail_found_duration`으로 따로 모은다.
- 날씨는 외부 API를 부르는 별도 요청이라 이 스크립트는 부르지 않는다.

### 행사 오픈 순간 신청 (`program-open.js`)

1. 준비 단계에서 관리자로 로그인하고, 신청 회원 `APPLICANTS`명을 50명씩 묶어 로그인시킨다.
2. 관리자 API로 행사를 새로 만든다. 신청 시작은 서버 시각 기준 `OPEN_DELAY`초 뒤, 결제 기한은 30분이다. 측정 중에 결제 만료 작업이 자리를 돌려주면 성공 수가 정원을 넘을 수 있어서 기한을 넉넉히 잡았다.
3. 모든 VU가 신청 시작 1초 뒤부터 0~500ms 사이에 흩어져 한 번씩 신청한다. 1초는 서버 시각을 초 단위 `Date` 헤더로만 알 수 있어서 둔 여유다. 신청마다 새 `Idempotency-Key`를 쓴다.
4. 판정: 201이 정확히 `CAPACITY`건이고, `PROGRAM_SOLD_OUT`이 아닌 그 밖의 응답이 0건이면 통과다. 매진 응답은 409라서 k6의 `http_req_failed`에는 실패로 잡히지만 판정에는 쓰지 않는다.
5. 끝나면 스크립트가 DB 대조 쿼리를 출력한다. 검증 서버의 MySQL에서 돌려 결과가 정원과 같은지 확인한다.

회마다 새 행사를 만들므로 같은 데이터로 여러 번 돌려도 된다.

## 3. 검증 환경 실행 절차

운영 서버와 운영 DB에서는 돌리지 않는다. 같은 리전에 임시 EC2 두 대를 만들고, 측정이 끝나면 바로 지운다.

1. **인스턴스**
   - 앱 서버: 운영과 같은 사양(t4g.small, arm64, EBS gp3 20GB)에 운영과 같은 compose 파일(`deploy/docker-compose.prod.yml`)로 앱·MySQL·Caddy를 띄운다.
   - k6 서버: 같은 리전, 같은 VPC에 한 대. 가상 사용자 2,000명을 띄울 메모리가 있는 사양을 고른다.
   - 보안 그룹: k6 서버에서 앱 서버 80 포트로 가는 연결만 연다. 접속은 SSM Session Manager로 한다.
2. **앱 서버 설정**
   - 운영 Parameter Store 값과 운영 데이터를 복사하지 않는다. DB 비밀번호 같은 값은 이 환경에서만 쓸 임시 값을 새로 만든다.
   - `SITE_ADDRESS=:80`으로 두어 Caddy가 인증서 없이 http로 받게 한다.
   - 메일·공공데이터 키는 가짜 값이라 관련 스케줄 작업은 실패한다. 측정 중에 이 작업이 도는지 로그로 확인하고 측정 조건에 적는다.
   - Grafana Alloy로 커넥션 풀·JVM 지표를 볼지 정한다. 보지 않으면 alloy 서비스를 빼고 띄운다.
3. **데이터**: 앱이 뜨고 마이그레이션이 끝나면 1절의 검증 서버 예시로 장소 100만 건과 신청 회원 2,000명을 넣는다.
4. **측정**: 시나리오마다 워밍업 1회 뒤 3회 측정하고 중앙값을 쓴다. 지도 조회와 행사 신청은 따로 돌린다.
5. **측정 조건 기록**: 데이터 규모, 인스턴스 사양(앱·k6), 커넥션 풀 크기(지금은 Hikari 기본값 10), 동시 사용자 수, 측정 시간, 측정 중 돈 스케줄 작업.
6. **정리**: EC2 두 대와 볼륨을 지우고, 남은 자원이 없는지 콘솔과 AWS Budgets로 확인한다.
